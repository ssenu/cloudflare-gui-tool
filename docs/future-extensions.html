🧭 확장 방안

1차 버전에서 제외했지만 나중에 추가할 수 있는 Cloudflare 기능들. 각 항목은 필요해지면 별도 스펙으로 발전시킨다.

1. Quick Tunnel (임시 URL)

난이도 낮음

무엇

로그인·설정 없이 cloudflared tunnel --url http://localhost:8000 한 번으로 임시 *.trycloudflare.com URL을 발급받는 기능.

언제 유용한가

개발 중인 서비스를 몇 분만 외부에 보여줄 때. 도메인/DNS 설정이 전혀 필요 없음.

구현 방안

메인 화면에 "빠른 공유" 버튼 → 포트만 입력 → 실행 → stdout에서 발급 URL 파싱해 표시 + 클립보드 복사. 프로세스 관리는 기존 process_mgr 재사용.

⚠ URL이 매번 바뀌고, Cloudflare가 안정성을 보장하지 않음 (프로덕션 부적합).

2. Cloudflare Access (Zero Trust 접근 보호)

난이도 중간API 토큰 필요

무엇

터널로 연 사이트에 이메일 OTP, Google 로그인 등 인증 관문을 걸어 아무나 접근하지 못하게 하는 기능.

언제 유용한가

관리자 페이지, 개인 대시보드, SSH 웹 터미널 등 본인만 쓰는 서비스를 외부에 열 때 사실상 필수적인 보안 계층.

구현 방안

Cloudflare API 토큰(Access: Apps and Policies 권한) 등록 → 터널 카드에 "보호 설정" 버튼 → Access Application + Policy(허용 이메일 목록)를 API로 생성. API 스코프 관리와 UI가 커져서 난이도 중간.

3. DNS 레코드 조회/정리

난이도 낮음~중간API 토큰 필요

무엇

route dns로 생긴 CNAME 레코드를 GUI에서 확인하고, 터널 삭제 시 남은 레코드를 함께 정리하는 기능.

언제 유용한가

터널을 만들고 지우다 보면 대시보드에 죽은 CNAME이 쌓이는데, 현재 cloudflared CLI로는 DNS 레코드 삭제가 불가능해 수동 정리해야 함.

구현 방안

Cloudflare API 토큰(Zone: DNS Edit 권한) 등록 → 존 레코드 조회 → 터널 ID(<uuid>.cfargotunnel.com)를 가리키는 CNAME 필터링 → 터널 삭제 플로우에 "DNS 레코드도 삭제" 체크박스 추가.

4. docker run 단독 컨테이너의 정확한 상태 판정

난이도 중간

무엇

현재 도커 서비스는 docker compose(compose 파일 기반) 단위로만 시작/정지/상태 판정을 한다. compose 없이 docker run으로 띄운 단독 컨테이너는 대상이 없어 지원하지 않는다.

언제 유용한가

compose 파일을 따로 관리하기 귀찮은 간단한 컨테이너 하나만 돌릴 때.

구현 방안

라우트 서버 종류에 "도커(단독)" 옵션 추가 → 컨테이너 이름 또는 이미지를 입력받아 docker run --name <고정이름> ...으로 시작 → 상태 판정은 docker inspect -f {{.State.Running}} <고정이름> 또는 docker ps --filter name=<고정이름>로 확인. compose 경로와 달리 "이 컨테이너가 이 라우트 소유"임을 식별할 고정 이름 규칙이 필요해 난이도가 약간 더 있음.

5. 라우트별 Cloudflare Access 설정

난이도 중간API 토큰 필요

무엇

위 2번(Cloudflare Access)을 터널 단위가 아니라 라우트(서브도메인) 단위로 세밀하게 적용하는 기능. 한 터널 안에서도 라우트마다 보호 여부/허용 이메일이 다를 수 있다(예: 관리자 페이지는 보호, 공개 API는 미보호).

언제 유용한가

v2부터 터널 하나에 라우트를 여러 개 등록할 수 있게 되면서, 라우트별로 접근 정책을 다르게 걸 필요가 커짐.

구현 방안

2번 항목의 API 연동을 라우트 카드 단위 UI로 확장 — 각 라우트에 "보호 설정" 버튼을 달고 Access Application의 대상 호스트네임을 해당 라우트의 hostname으로 지정. 2번이 선행되어야 하는 종속 항목.

6. 여러 대상 머신 동시 모니터링

난이도 중간~높음

무엇

현재는 한 번에 하나의 대상(로컬 또는 SSH 프로필 하나)만 전환해서 볼 수 있다. 등록된 모든 머신(로컬 + SSH 프로필들)의 터널/서비스 상태를 한 화면에 요약해서 보여주는 뷰.

언제 유용한가

SSH 대상이 여러 대로 늘어났을 때 하나씩 전환하며 확인하는 대신 전체 현황을 한눈에 보고 싶을 때.

구현 방안

대상마다 별도 RunRegistry/ProcessManager를 두고 폴링을 병렬화(SSH는 특히 왕복 지연이 크므로 순차 폴링 시 UI가 느려짐) → 요약 카드 또는 트리 뷰로 표시. 병렬 SSH 폴링과 실패한 대상의 처리(연결 끊김 표시)가 필요해 난이도 중간~높음.

7. 기타 아이디어 메모

  • Windows 서비스 모드: GUI 없이 OS 부팅 시 터널 자동 시작 (cloudflared service install). v2부터 GUI 종료와 터널 생존은 이미 분리되어 있으므로, 이 항목은 "OS 재부팅에도 자동으로 다시 뜨게" 하는 것이 남은 과제.
  • 트레이 아이콘: 창을 닫아도 트레이에 상주하며 빠르게 상태를 보고 on/off할 수 있는 진입점. v2에서는 창을 그냥 닫아도 터널이 유지되므로 트레이 아이콘의 역할은 "편의 진입점"으로 축소됨.
  • 메트릭 대시보드: cloudflared --metrics 엔드포인트로 요청 수/지연시간 그래프 표시.
